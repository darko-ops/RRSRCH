    The four sentences that carry every technical answer

    1. Restate. “So you want X, given Y — is Z in scope?” Buys thinking time and catches misreads for free.
    2. Name the approach and its cost. “I'd do A. It's simpler, and it costs us B.”

    Your project, told well

    Walk me through the architecture end to end.

    Testing Whether you understand the whole system or just the file you last edited. They want the request path, not a component inventory.

    Trace one request, don't list technologies:

    1. Browser loads the CRA bundle from Vercel's CDN. vercel.json rewrites everything that isn't /api/* to index.html, because the client does its own routing.
    2. The React app calls /api/.... That rewrite points at api/index.js, which is three lines — it just exports the Express app so Vercel can invoke it per request.
    3. Express authenticates the caller from a Bearer token, verifies an HMAC over the payload, loads the account, and serves or writes.
    4. The Python side is separate: FastAPI + an MCP server over the same corpus, talking to Postgres through async SQLAlchemy, with pgvector for vector kNN and pg_trgm for lexical kNN.

    Then name the seam that matters: the Node API is stateless by necessity — it runs as a serverless function, so there's no process to keep a session in and no writable disk. That single constraint explains most of the design decisions below, and saying it up front makes the rest sound intentional rather than improvised.

    Why three stacks? Isn't that over-engineered for one product?

    Testing Whether you chose or just accumulated. A defensible “yes, partly” beats a defensive “no”.

    Answer honestly, with the split drawn along a real line: the Python service exists because the retrieval work lives there — sentence-transformers, numpy, pgvector, an eval harness. Reimplementing embeddings and a reranker in Node to avoid a second language would have been the actual over-engineering. The Node API is a thin edge: auth, accounts, publishing, and proxying. The boundary is “does this need the ML ecosystem?”

    Then concede the real cost, because there is one: two deploy targets, two dependency sets, and no shared type definitions across the seam — a schema change has to be made twice by hand. If you were starting again with a team, that's the argument for collapsing to one language or generating clients from an OpenAPI spec.

    What's the part you'd rewrite first?

    Testing Self-assessment. Candidates who can't criticise their own code usually can't review anyone else's either.

    Pick a real one and be concrete. Strongest options in your repo:

    • The Blob user store. Storing accounts as a JSON array in blob storage means every signup is a full read–modify–write with last-write-wins on concurrent registration. It was the right call to ship without provisioning a database; it is not the right call to keep. Postgres with a unique index on email replaces the whole mechanism — and you already run Postgres for the Python side.
    • App.js at ~1,970 lines. One component holding 40-odd useState/useEffect calls. The fix is extracting data-fetching into hooks and splitting by route, not a rewrite.
    • No rate limiting on login. It's the first thing you'd add before real users, and knowing that unprompted reads well.

    The pattern: name it, say why it was acceptable at the time, say exactly what replaces it.

    Where does this fall over at 100× the traffic?

    Testing Whether you can find your own bottleneck. Every system has one; not knowing yours is the bad answer.

    Your bottleneck is unambiguous, so say it fast: the JSON-blob account store. Every authenticated request calls readUsers(), which lists a blob prefix and downloads the entire user file. That's O(all users) work per request, and writes are a full-file rewrite with no locking — two concurrent signups and one is silently lost.

    The fix is not caching, it's the right store: users in Postgres, indexed by id and email, one row read per request. After that the next constraints are cold starts on the serverless functions and embedding inference on the Python side — which is why encode() is already pushed off the event loop rather than blocking the async request path.

    Tell me about the hardest bug you've fixed in it.

    Testing Debugging method under pressure. They want the reasoning trail, not the patch.

    Use the blob-read incident — it's a genuinely good story because the symptom lied. Structure it tightly:

    • Symptom. Users were being logged out. Tokens verified fine, but the account lookup found nothing.
    • The misleading part. Every failure path in the read returned an empty array, so “the store is empty” and “we couldn't read the store” looked identical from the outside. Those need opposite responses — one needs a restore, the other needs a credential.
    • First fix was diagnostic, not behavioural. Made each failure path say which one it was, without logging the secret-derived prefix. Callers still got []; only the silence changed.
    • Root cause. The code fetched the blob's public CDN URL anonymously; the edge started refusing it with a 403. The accounts had been there the whole time.
    • Real fix. Read through the SDK with the store token instead of an anonymous URL, and bypass the cache so a stale or poisoned edge entry couldn't repeat it.

    The line to land: “the bug was that a failure was indistinguishable from a normal result.” That's an observability lesson, and it generalises — which is what makes it interview-grade rather than trivia about one vendor's CDN.

    03 — LANGUAGE

    JavaScript they will actually ask about

    Fundamentals round. Short questions with a right answer, used to calibrate before the harder rounds. Answer crisply and move on — over-explaining here reads as padding.

    Explain the event loop. Predict the output of a snippet mixing setTimeout, a promise, and sync code.

    Testing The single most-asked JS question. They want “microtasks drain before the next macrotask” and the ability to trace it.

    JS runs one call stack. When the stack empties, the runtime drains the microtask queue completely (promise callbacks, queueMicrotask), then takes one macrotask (timers, I/O) and repeats. So promise callbacks always run before a setTimeout(...,0) queued at the same moment.

    console.log('1');
setTimeout(() => console.log('2'), 0);
Promise.resolve().then(() => console.log('3'));
console.log('4');
// 1, 4, 3, 2

    Sync code first (1, 4), then the microtask (3), then the timer (2). If they push further: in Node, process.nextTick drains before promise microtasks, and setImmediate fires in the check phase after I/O callbacks.

    Bring it back to your code if it fits — this is exactly why the Python side pushes model inference off the event loop: a blocking CPU call in an async handler stalls every other in-flight request, and the same is true of a synchronous bcrypt.hashSync in Express.

    What is a closure, and where have you actually used one?

    Testing Whether you understand scope capture or just memorised a definition. The “where did you use one” half is the real question.

    A closure is a function plus the scope it was defined in, kept alive after that outer scope returns. Definition, then a use:

    function rateLimiter(maxPerMinute) {
  const hits = new Map();                 // captured, private
  return (key) => {
    const now = Date.now();
    const recent = (hits.get(key) || []).filter(t => now - t < 60_000);
    if (recent.length >= maxPerMinute) return false;
    hits.set(key, [...recent, now]);
    return true;
  };
}

    hits survives the call and is unreachable from outside — that's the point. Nice bonus: this is exactly the rate limiter your login endpoint is missing, so it doubles as a real answer if they ask what you'd harden first.

    Classic follow-up: var in a loop with setTimeout prints the final value every time because all three closures share one binding; let creates a fresh binding per iteration and prints 0, 1, 2.

    == vs ===, and how would you compare two secrets?

    Testing Basic knowledge, then whether security instinct shows up unprompted. The second half is the differentiator.

    == coerces before comparing ('1' == 1, null == undefined, and the famous [] == false); === compares type and value. Use ===, except the idiomatic x == null to catch both null and undefined.

    For secrets, neither: === on strings short-circuits at the first differing byte, which leaks length and prefix through timing. Use a constant-time compare on equal-length buffers — which is what your token verification does at server.js:626, checking length first because timingSafeEqual throws on a length mismatch.

    How do you handle errors across several async calls?

    Testing Practical async competence. They're watching for unhandled rejections and for whether you know the Promise combinators.

    • Promise.all — rejects on the first failure, and the other promises keep running unobserved. Right when you need every result.
    • Promise.allSettled — always resolves with per-item status. Right when partial success is useful, like fanning out to several market-data providers where one being down shouldn't blank the page.
    • Promise.race / any — first settled / first fulfilled. race against a timeout is the standard deadline pattern.

    In Express 4 specifically, an async handler that throws does not reach the error middleware — the rejection is unhandled and the request hangs until it times out. That's why every handler in your server.js wraps its body in try/catch and returns a 500 explicitly. Express 5 fixes this by forwarding rejected promises to next(); in 4 you either keep the try/catch or wrap handlers in an asyncHandler helper. Saying this shows you've actually run Express in production.

    What would TypeScript have bought you here?

    Testing Whether you can argue types as engineering, not fashion. Most full-stack roles are TS-first, so this is often a fit question in disguise.

    Be concrete about your own seams. The Express API and the React client agree on response shapes by convention only — nothing catches it when publicUser drops a field the UI still renders. Shared types across that boundary is the highest-value change, and it's cheap: define the response types once, import them on both sides.

    Then show you know the limits: types don't validate untrusted input. Whatever the compiler thinks, req.body is unknown at runtime, so you still need a parse step at the boundary — which is precisely what the Python side already does with Pydantic. The pattern is validate at the edge, trust types inside. If asked what you'd reach for in Node: Zod, for the same reason.

    Deep clone an object. What breaks?

    Testing Whether you know the standard tool and its edges, rather than reflexively reaching for the JSON trick.

    structuredClone(obj) is the modern answer — it handles Date, Map, Set, ArrayBuffer, and cyclic references. It throws on functions, DOM nodes, and class prototypes (you get a plain object back).

    JSON.parse(JSON.stringify(x)) silently corrupts data: Date becomes a string, undefined and functions vanish from objects, NaN and Infinity become null, Map/Set become {}, and cycles throw. Fine for known-flat JSON, wrong as a default.

    Spread and Object.assign are shallow — a nested object is shared, which is a real bug source in React state where mutating a nested field of a “copy” skips the re-render.

    04 — FRONT END

    React and the front end

    You're on React 19 with a 1,970-line App.js and a three.js scene in AtlasView.js. Both are assets: one gives you a real refactoring conversation, the other a real performance one.

    Why does React need keys in a list, and why is the array index a bad one?

    Testing Reconciliation. Extremely common, and the wrong answer (“for performance”) misses that it's a correctness issue.

    Keys tell React which element in the new list corresponds to which in the old one. Without a stable identity React matches by position, so it reuses the wrong component instance — it doesn't just re-render more, it renders wrong.

    Concretely: a list of items each with an uncontrolled input, keyed by index. Delete the first item and every element shifts up by one; React sees the same keys 0..n-1 in the same positions and keeps the existing DOM nodes and state, so the text you typed into row 1 is now sitting in row 0's input. Key by item.id and React moves the node instead.

    Index keys are fine only when the list is append-only and never reordered, filtered, or deleted from.

    useMemo, useCallback, React.memo — when do they actually help?

    Testing Whether you measure or cargo-cult. The strong answer includes “usually not”.

    Each has a real cost — a dependency array to keep correct and memory held across renders. Defaults: don't, until a profile says otherwise. The three cases where they earn their place:

    • Genuinely expensive computation per render — sorting or filtering thousands of rows, or the derived geometry in your AtlasView.js, where four useMemo calls stop node and edge layouts being rebuilt every frame. That's the textbook justified use.
    • Referential identity feeding a memoised child or an effect. A fresh object or callback each render defeats React.memo and re-fires useEffect. Here useCallback is about correctness of the dependency graph, not speed.
    • A context value, so every consumer doesn't re-render whenever the provider does.

    Then mention the direction of travel: the React Compiler auto-memoises this pattern, which is exactly why hand-memoising everything ahead of a measurement is poor value. Note that React.memo is a shallow prop compare — it does nothing if you pass a new inline object every render.

    Your App.js is nearly 2,000 lines with dozens of hooks. How would you break it up?

    Testing This is the one they'll actually ask if they read your repo. It's not a gotcha — they want to see how you refactor safely.

    Don't get defensive; give a sequenced plan, smallest risk first:

    1. Extract data-fetching into custom hooks — useAccount(), useAtlasList(). Each owns its loading, error, and abort handling. This alone removes most of the useEffect calls and makes them individually testable.
    2. Split by route. The dashboard, the account page, and the Atlas view are separate screens sharing one component only because they were built together. Splitting them lets you code-split too, so the three.js bundle isn't paid for by someone visiting the login page.
    3. Lift shared server state into one place. Whether that's context plus a reducer or a data library, the goal is that “who is signed in” has exactly one owner.
    4. Leave presentational JSX until last. It's the largest and least risky part; moving it early creates a big diff that hides real changes.

    Close with the guardrail: a 2,000-line component with no tests can't be refactored confidently, so the first commit is a couple of smoke tests around the flows you're about to touch — then the moves are verifiable.

    How do you fetch data in an effect without race conditions or setting state after unmount?

    Testing Very common practical bug. They want cleanup and cancellation, not just fetch().then(setState).

    The bug: a user types fast, two requests are in flight, the slower one resolves last and overwrites the newer result with stale data. Order of resolution is not order of dispatch.

    useEffect(() => {
  const ac = new AbortController();
  (async () => {
    try {
      const res = await fetch(`/api/account/atlas/${slug}`, { signal: ac.signal });
      if (!res.ok) throw new Error(`HTTP ${res.status}`);
      setData(await res.json());
    } catch (err) {
      if (err.name !== 'AbortError') setError(err);
    }
  })();
  return () => ac.abort();       // runs on slug change AND on unmount
}, [slug]);

    The cleanup solves both problems at once: the previous request is cancelled before the next starts, and an unmount aborts the in-flight one. An ignore boolean also works if you can't cancel, but AbortController actually stops the request.

    Worth adding: in React 19, effects run twice in development StrictMode specifically to surface missing cleanup. If double-mounting breaks your effect, the effect was already broken.

    Controlled vs uncontrolled components — which do you reach for?

    Testing Everyday React judgment, and a chance to see if you know the perf cost of controlling everything.

    Controlled: React state is the source of truth (value + onChange). Uncontrolled: the DOM holds the value and you read it via a ref or on submit.

    Reach for controlled when the value drives other UI as it changes — live validation, a disabled submit button, a filtered list. Reach for uncontrolled when you only need the value at submit time; it's less code and avoids a re-render per keystroke, which matters in a large form.

    The trap: switching a component between the two by passing value={undefined}, which React warns about loudly. Give inputs value={x ?? ''} when x may be null.

    What's new in React 19 that you'd actually use?

    Testing Whether “React 19” in your package.json is a version bump or a decision. Naming two features you'd use beats reciting the changelog.

    • Actions and useActionState — pending state, errors, and optimistic updates for form submission handled by the framework instead of three useState calls per form. Directly applicable to your signup and login forms.
    • use() — read a promise or context conditionally, which removes a class of “fetch in an effect, store in state” boilerplate.
    • Ref as a prop — forwardRef is no longer needed for most components.
    • Better hydration errors and native support for document metadata and stylesheets rendered from components.

    Honest framing if pressed: you're on react-scripts, so you're getting React 19 the library without the server-side pieces. CRA is deprecated, and the migration you'd plan is to Vite for a dev-server and build story that's actively maintained — Next.js only if you actually want SSR, which a dashboard behind a login mostly doesn't.

    How do you keep a three.js scene from tanking the frame rate in React?

    Testing Bonus round if they notice @react-three/fiber. Real answer: React state and a render loop are different clocks.

    The core rule: never drive per-frame animation through React state. setState at 60fps means 60 reconciliations a second. Inside useFrame, mutate the object directly — meshRef.current.position.x = … — and let the renderer read it. React owns the scene graph's structure; the frame loop owns its values.

    Beyond that: memoise geometries and materials so they aren't reallocated per render (each one is a GPU allocation), dispose them on unmount to avoid leaking, instance repeated nodes rather than mounting hundreds of meshes, and lazy-load the whole view with React.lazy so three.js stays out of the initial bundle.

    How would you make this accessible, and how would you know it worked?

    Testing Increasingly a standard screen. The failure mode is listing rules with no verification step.

    Basics: semantic elements over divs with click handlers (a real button gets keyboard and screen-reader behaviour for free), every input tied to a label, visible focus states, meaningful alt text, and colour never as the sole signal.

    Then the part most candidates skip — how you verify: tab through the flow with no mouse, run axe or Lighthouse in CI, and test with Testing Library queries by role and label rather than test IDs, so an inaccessible component literally fails its own test. That last point lands well because you already have Testing Library installed.

    For a canvas-based view like the Atlas, the honest answer is that a WebGL scene is opaque to assistive tech, so it needs a parallel accessible representation — a list or table of the same nodes and edges — not an aria-label on the canvas.

    05 — BACK END

    Node, Express, and API design

    Your API is small but unusually opinionated: stateless by necessity, versioned writes, an explicit device-pairing flow. That's a lot of surface to be asked about.

    What is middleware in Express, and what does ordering change?

    Testing Whether you understand the request pipeline. Ordering bugs are the classic Express production incident.

    Middleware is (req, res, next) functions run in registration order; each either responds or calls next(). Error middleware takes four arguments and only runs when something calls next(err).

    Order is the whole design. In your server.js the stack is CORS → body parser → session → passport → routes, and that sequence is required: CORS has to handle the preflight before anything can reject the request, and passport can't read a session that hasn't been attached yet. Register a body parser after your routes and req.body is undefined in every one of them.

    A detail worth volunteering: you raised the JSON limit to 1 MB deliberately because Atlas graphs exceed the 100 KB default. That's a good answer to “how do you stop a client sending you a 2 GB body” — a bounded limit is a security control, not just a config value.

    Design a REST endpoint for creating a resource. What status codes and what makes it safe to retry?

    Testing API judgment. Idempotency is the word they're listening for.

    POST /api/atlas returns 201 with the created resource and a Location header; 400 for a malformed body, 401 unauthenticated, 403 authenticated but not allowed, 404 for a missing parent, 409 for a conflict such as a duplicate email (which is what your signup returns), 422 if you distinguish semantic validation from parse failure, 429 rate limited.

    On retries: GET, PUT, and DELETE are idempotent by definition; POST is not, so a client that times out and retries can create two resources. The fix is an Idempotency-Key header the server records with the result, returning the original response on a repeat. Alternatively make creation a PUT to a client-chosen id — which is effectively what your Atlas publishing does by keying on a slug, so a republish overwrites rather than duplicating.

    If they push on pagination: cursor-based, not OFFSET. Offset pagination gets slower the deeper you go and skips or repeats rows when the underlying list changes between pages.

    Your API runs serverless. What does that change about how you write it?

    Testing Whether you know your own deployment model. Very likely to be asked because api/index.js is three lines and obviously deliberate.

    Four things stop being available, and each has a visible consequence in your code:

    • No process memory between requests. An in-memory session store or cache is per-instance and effectively random. That's why account auth uses stateless signed tokens rather than the express-session store used for the Google OAuth path.
    • No writable disk. The local JSON fallback silently reads nothing in production — which is exactly the failure your logging now calls out by name at server.js:585.
    • No background work after the response. The instance can be frozen the moment you respond, so “fire and forget” work may never run. It needs a queue.
    • Cold starts and connection limits. Each concurrent invocation is its own instance, so naive per-request database connections exhaust Postgres fast — hence connection pooling at the proxy layer rather than in the function.

    Say the tradeoff plainly: you get zero-ops scaling and pay for it with statelessness. It suits a read-mostly API in front of a shared store, and it's a poor fit for long-lived connections like WebSockets.

    You write a JSON file to blob storage and immediately read it back — you get the old version. Why, and how do you fix it?

    Testing Distributed-systems instinct. This is your real war story, and it maps onto a classic caching question.

    The write went to origin; the read was served by a CDN edge still holding the previous object for that key. Overwriting the same path means the cached copy is stale for as long as its TTL — up to about a minute in practice. For a cache of article text that's harmless. For an account store it's fatal: a user signs up, the next request reads the pre-signup version, and the account doesn't exist.

    Two fixes, and knowing both is the point:

    • Never overwrite a key. Every write lands at a new immutable path — yours are zero-padded millisecond timestamps, so lexicographic max is the newest version. Reads list the prefix and fetch that unique URL, which was never cached under a stale value. Old versions are pruned best-effort. This is content-addressed writing, and it's the same reason bundlers emit hashed filenames.
    • Read from origin, authenticated. Fetch through the SDK with the store token and cache disabled, so no edge copy is involved.

    Then name the general principle, which is what they're actually buying: read-after-write consistency is not free, and caches are correct only for data that tolerates being stale. Authentication data does not.

    How do you decide what to log, and what must never be logged?

    Testing Operational maturity. Rare enough to be a strong differentiator.

    Log at the decision points where two different causes could produce the same outcome — that's the whole lesson from your blob incident. A read that returns [] should say whether the store was empty or unreadable, because those need opposite responses.

    Match level to ownership, which your requireUser already does: a rejected token is warn, because it's the caller's problem and the ordinary case; a valid token for an unknown user is error, because reaching that line required a real signature, so it's almost certainly the store failing to load. Including the loaded user count makes the log self-diagnosing — zero means the store came back empty, non-zero means that one record is genuinely gone.

    Never logged: passwords or hashes, tokens or session ids, the secret-derived blob prefix (an unguessable path is a credential — logging it destroys the property it relies on), and personal data beyond an opaque user id. Structured JSON with a request id so one request can be traced end to end.

    Walk me through your device-pairing flow. Why not just ask for the password?

    Testing Whether you can explain an auth protocol you implemented, and whether you know why it exists.

    It's the OAuth device authorization grant, for a client that can't safely show a browser or accept a password — a CLI or an agent on another machine. The flow:

    1. Device calls /api/device/start and gets a short human-readable user_code, an opaque device_code, a verification URL, and a poll interval.
    2. The human types that code into an already-authenticated browser session and approves it.
    3. The device polls /api/device/poll with its device_code and gets a long-lived token once approved.

    Design details worth volunteering, because they're the reason it's a good implementation: the user code alphabet excludes 0/O/1/I/L so a code read aloud can't be mistyped; the pairing is single-use (consumed) and TTL-bounded; and the approving user must already be authenticated, so the code alone grants nothing. Crucially, the token carries a device id and the device stays on the account record, which is the revocation list — that's how you get revocable credentials out of otherwise stateless tokens. Deleting the device invalidates its token on the next request.

    Why not the password: it would put a long-lived, reusable, all-powerful credential on a machine you may not control, with no way to revoke it short of a password reset that logs out everything.

    06 — SECURITY

    Auth and security

    Your strongest technical territory, and the most probeable: you hand-rolled an HMAC token scheme, a capability-URL store, and a device grant. Expect them to push. The winning move is knowing your own weaknesses before they name them.

    You built your own token instead of using a JWT library. Defend that.

    Testing Whether “I wrote it myself” is arrogance or a considered scope decision. They're mostly checking you didn't make a classic crypto mistake.

    Start by showing you know what you built: it's a JWT-shaped token — base64url payload, dot, HMAC-SHA256 over that payload — minus the header. Symmetric signing, verified per request, with an exp claim checked on every verify.

    The defensible reasons: a single service signing and verifying with one secret has no need for JWT's algorithm negotiation, and that negotiation is the historical vulnerability — the alg: none and RS256-confused-for-HS256 attacks both come from trusting an attacker-supplied header. Your verifier hardcodes the algorithm, so that class of bug is structurally absent.

    Then show the care in the details, unprompted: the comparison is timingSafeEqual with a length check first, because that function throws on unequal lengths; the payload is decoded only after the MAC verifies, so you never parse untrusted JSON you haven't authenticated.

    And concede the honest limit: rolling your own is right for one service and wrong the moment a second service needs to verify these tokens, or you want asymmetric keys so verifiers can't mint. At that point it's a library and a JWKS endpoint. Framing it as “correct at this scope, replaced at that scope” is exactly the judgment they're testing.

    Your tokens last 30 days — a year for devices — and can't be revoked. Is that OK?

    Testing The known weakness of stateless auth. Denying it is the only wrong answer.

    Concede it directly: a stateless token is valid until it expires, so a leaked one is usable for its full lifetime. There's no logout that invalidates it server-side — the client just forgets it.

    Then show you've already solved half of it: device tokens are revocable, because they carry a device id checked against the account's device list on every request. Removing the device kills the token immediately. That's the standard pattern — a small piece of server state converts a stateless token into a revocable one.

    What you'd do properly: short-lived access tokens (15 minutes) plus a longer refresh token that's stored and revocable, and a token_version on the user record bumped on password change so every outstanding token dies at once. Then note the tradeoff honestly — each of those adds a store lookup, which is the statelessness you bought serverless deployment with. That's the trade, not an oversight.

    Why bcrypt? Why not SHA-256? What's the cost factor for?

    Testing Password storage fundamentals. Nearly guaranteed if they see bcrypt in your dependencies.

    SHA-256 is designed to be fast, which is precisely wrong for passwords — commodity hardware does billions of guesses a second against a stolen hash table. bcrypt is deliberately slow and its cost factor is tunable, so you can keep raising the attacker's cost as hardware improves without changing the scheme. It also salts each hash automatically, so identical passwords produce different hashes and one rainbow table can't cover your whole user table.

    Cost 10 (yours) is about 100 ms per hash — a reasonable floor; 12 is a common current recommendation. The upper bound is your own login latency and CPU, and on serverless it's also your invocation time. Note the real constraint: bcrypt is CPU-bound, so the async version matters — bcrypt.hashSync in an Express handler blocks the event loop for every concurrent request, which is a self-inflicted denial of service. Your code uses the promise API correctly.

    If they push further: Argon2id is the current preference because it's memory-hard, which blunts GPU and ASIC attacks in a way bcrypt's CPU cost doesn't. bcrypt remains perfectly acceptable; scrypt is the other memory-hard option. What is not acceptable is a plain fast hash, salted or otherwise.

    What is a capability URL, and what are you relying on?

    Testing Whether you understand the security model you chose, including what breaks it. A great question to get, because most candidates have never had to think about it.

    Your blob store is public-by-URL, so the user file lives at a path derived by hashing a secret: users-<sha256(secret)[0:40]>/. The path itself is the credential — knowing it grants read access, and 160 bits of it is not guessable.

    What that relies on, and you should list it before they do: the URL never appears in a log, a referrer header, an error page, a bug report, or a Git commit. It can't be revoked without moving the data. And it grants access to whoever holds it — there's no per-user authorisation, so it's all-or-nothing.

    The mitigations you already have: the file holds bcrypt hashes only, never plaintext, so reading it isn't instantly game over; and the code deliberately keeps that prefix out of logs even in the error paths. Rotating the secret both invalidates every token and moves the store — a documented consequence, and a good example of a coupling you'd design out later by separating the signing key from the storage key.

    Where it goes at scale: a private store with authenticated reads, which is the direction the SDK read already moved in.

    Your login endpoint has no rate limiting. Walk me through the attack and the fix.

    Testing Whether you can threat-model your own code. You already know this gap — own it fast and spend the time on the fix.

    The attack is credential stuffing: take a breach dump of email/password pairs and replay it as fast as the endpoint will answer. No lockout means the only limit is your throughput. Bcrypt at cost 10 helps a little — it caps guesses per second — but that cuts both ways, since each attempt also burns 100 ms of your CPU, so the same endpoint is a cheap resource-exhaustion vector.

    Layered fix, cheapest first:

    • Rate limit per IP and per account — per-IP alone is defeated by a botnet, per-account alone lets one IP spray many accounts.
    • Exponential backoff or a temporary lock after repeated failures on one account.
    • A CAPTCHA or proof-of-work step once a threshold trips, rather than a hard lock that becomes a denial-of-service against the real user.
    • Alert on the shape of the traffic — many accounts, few attempts each, one source — because that's what stuffing looks like and a per-account limit won't catch it.

    One more thing to volunteer: your login returns a generic failure regardless of whether the email exists, which is correct — distinct messages turn the login form into an account-enumeration oracle. Signup necessarily leaks that with its 409, which is the usual accepted tradeoff.

    Explain CORS. Your config sets a single origin and credentials: true — why not *?

    Testing Whether you understand the browser's rules or just copy config until the error goes away. Extremely common.

    CORS is a browser restriction, not a server one: the browser refuses to let page JS read a cross-origin response unless the server's headers permit that origin. It protects users from a malicious page reading their authenticated data on another site. It is not access control — curl and any server ignore it entirely, so it never substitutes for authorisation.

    You can't use * with credentials: the spec forbids the combination, precisely because a wildcard plus cookies would let any site make authenticated requests on the user's behalf. With credentials: true you must echo one specific origin, which is what your config does from FRONTEND_URL.

    Worth adding: non-simple requests get a preflight OPTIONS first, which is why CORS must be registered before anything that could reject the request; and reflecting the request's own Origin back is the common “fix” that quietly disables the protection entirely — it's an allowlist or nothing.

    How do you prevent XSS, CSRF, and SQL injection?

    Testing The security baseline. Give the mechanism, not the name.

    • SQL injection — parameterised queries, never string interpolation. SQLAlchemy's expression language on your Python side binds parameters, so this is structurally handled; the danger returns the moment someone builds raw SQL with an f-string. ORM use isn't the protection; parameter binding is.
    • XSS — React escapes interpolated values by default, so the main risk is dangerouslySetInnerHTML (sanitise with DOMPurify if you must render user HTML) and javascript: URLs in href. A Content-Security-Policy is the second layer for when the first fails.
    • CSRF — only affects credentials the browser attaches automatically, which means cookies. Your account API sends a Bearer token from JS, so it's structurally immune. Your Google OAuth path uses a session cookie and is not — that one wants SameSite=Lax (or a token) as its defence. Naming this distinction is the strong answer, because it shows you're reasoning about the mechanism rather than reciting a checklist.

    Round it out with headers you'd set: Strict-Transport-Security, X-Content-Type-Options: nosniff, and cookies as httpOnly, secure, SameSite — which your session config already does.

    A secret gets committed to the repo. What do you do?

    Testing Incident response. There is one right first move and most people get it wrong.

    Rotate the secret first. Not scrub history — rotate. The moment it was pushed it must be assumed compromised; scrubbing history is cosmetic and gives false comfort while the live credential is still valid. Bots scan public pushes within seconds.

    Then, in order: revoke the old credential at the provider, check access logs for use during the exposure window, remove it from history if the repo is public or the history is shared, and add a pre-commit secret scanner plus a .gitignore entry so it can't recur. Finally, ask why a human could commit it at all — the durable fix is that secrets only ever live in the environment, which is how your code reads every one of them.

    Worth noting for your own repo: the fallbacks like process.env.SESSION_SECRET || 'rrsrch-secret-key-2025' are a related risk — a missing env var doesn't fail loudly, it silently signs tokens with a value that's public in the source. In production that default should throw at boot instead. Saying this before they find it is a strong move.

    07 — DATA

    Data, SQL, and retrieval

    Expect standard SQL questions plus, because it's in your repo, real curiosity about pgvector and hybrid search. The vector work is genuinely differentiating — most full-stack candidates can't discuss it.

    When does an index help, and when does it hurt?

    Testing Table stakes for anyone claiming backend. They want the write cost named, not just “indexes make reads fast”.

    An index is a sorted structure the planner can seek into instead of scanning. It helps equality and range lookups, joins on the indexed column, and ORDER BY that matches its order.

    The costs: every insert, update, and delete maintains every index on the table, so write-heavy tables pay per index. They consume storage and memory. And the planner will ignore one if it estimates a large fraction of rows will match — a sequential scan genuinely is faster then, because random I/O per row costs more than a straight read.

    Things that quietly disable an index: wrapping the column in a function (WHERE lower(email) = … needs an expression index on lower(email)), a leading wildcard LIKE '%foo', and a type mismatch that forces a cast. On composite indexes, order matters — (a, b) serves WHERE a and WHERE a AND b, but not WHERE b alone.

    Close with the method: EXPLAIN ANALYZE, and compare estimated to actual rows — a large gap usually means stale statistics, not a missing index.

    What's an N+1 query and how do you find one?

    Testing The most common real-world ORM performance bug.

    One query fetches N rows, then accessing a relation on each row fires one more query — 1 + N round trips where 2 would do. It's invisible in development with ten rows and fatal in production with ten thousand, because the cost is network round trips, not database work.

    Fix by telling the ORM you want the relation up front — in SQLAlchemy, selectinload (a second query with IN, usually the right default) or joinedload (a single join, better for many-to-one, but it multiplies rows on collections). Or drop to one explicit query with a join and map the results yourself.

    Finding it: log SQL in development and watch the count per request, or use an APM that flags repeated identical query shapes. The tell is a query executed many times with only the bound parameter changing.

    How would you model this in SQL — and what would you index?

    Testing Practical schema design. They usually give you a small domain and watch for keys, constraints, and nullability.

    Use your own migration off the blob store as the worked example:

    CREATE TABLE users (
  id            uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  email         citext NOT NULL UNIQUE,      -- case-insensitive, unique
  password_hash text   NOT NULL,
  name          text   NOT NULL,
  created_at    timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE devices (
  id         uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  user_id    uuid NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  name       text NOT NULL,
  paired_at  timestamptz NOT NULL DEFAULT now(),
  revoked_at timestamptz
);
CREATE INDEX ON devices (user_id) WHERE revoked_at IS NULL;

    Point at the decisions rather than the syntax: the unique index on email is what makes concurrent signup safe — the database rejects the duplicate, which is a guarantee your read-modify-write blob store cannot give at any level of application care. ON DELETE CASCADE means account deletion can't leave orphaned devices. timestamptz not timestamp, always. And the partial index only covers live devices, since that's the only thing the auth path queries.

    Volunteering “this constraint is why the race disappears” is worth more than a perfect schema, because it shows you know what a database is for.

    Explain transactions and isolation levels.

    Testing Depth. Fine to say where your practical experience ends — but know what the levels prevent.

    ACID in one line each: atomic (all or nothing), consistent (constraints hold at commit), isolated (concurrent transactions don't see each other's partial work), durable (committed survives a crash).

    Isolation levels are a ladder of anomalies prevented: read committed (Postgres default) stops dirty reads but allows a value to change between two reads in the same transaction; repeatable read gives a consistent snapshot for the whole transaction; serializable guarantees the outcome matches some serial order, at the cost of transactions that fail and must be retried.

    The practical point is what it looks like in code: read-modify-write is a race at read committed — two concurrent balance updates lose one. Fix with SELECT … FOR UPDATE, an atomic UPDATE … SET n = n + 1, or serializable plus a retry loop. Then connect it: your blob user store is exactly this race with no database to arbitrate it — two simultaneous signups both read the array, both append, and the second write erases the first. That's a strong close, because it's the same bug at a layer you actually own.

    What is pgvector doing, and why hybrid search rather than pure vector similarity?

    Testing Your differentiator. Most candidates can't answer this at all, so a clear explanation is disproportionately valuable.

    Explain in layers, plain first: an embedding model maps text to a vector so that semantically similar text lands nearby, and cosine similarity measures that. pgvector adds the column type and the distance operators to Postgres, so retrieval is a normal SQL query against the same database as everything else — no separate vector store to keep in sync.

    Why hybrid: vectors are good at paraphrase and bad at exact tokens. Ask about a specific error code, version number, or identifier and pure vector search happily returns something “about the same topic” but wrong. Lexical matching — trigram similarity via pg_trgm in your case — is the opposite: exact on tokens, blind to paraphrase. So your store returns the union of vector kNN and lexical kNN as a candidate pool, and the engine fuses the two scores at 0.7/0.3.

    Then the part that shows judgment, because it's a product decision rather than a technique: a hard scope gate runs before any similarity is considered. If the query is scoped to Rust and the candidate is scoped to CSS, it's rejected outright no matter how similar the embeddings are. The reasoning is asymmetric risk — a miss costs a re-derivation, a false hit serves a confidently wrong answer. The threshold is tuned so false hits stay at zero, and CI fails if that regresses.

    If they go deeper: index choice is HNSW versus IVFFlat, and the tradeoff is recall against build time and memory — both are approximate, so you're trading exactness for speed and should measure recall, not assume it.

    How do you run a schema migration with zero downtime?

    Testing Whether you've shipped against a live database. Alembic in your dependencies invites this.

    The principle: old and new code run simultaneously during a deploy, so every migration must be backward compatible with the currently running version. That forces the expand–migrate–contract pattern:

    1. Expand — add the new nullable column or table. Old code ignores it.
    2. Backfill in batches, not one long transaction that locks the table.
    3. Migrate — deploy code that writes both and reads the new.
    4. Contract — once no running code touches it, drop the old column.

    A rename is never one step; it's add, dual-write, backfill, switch reads, drop. Specific Postgres hazards worth naming: adding a column with a volatile default rewrites the table, CREATE INDEX locks writes unless you use CONCURRENTLY, and any DDL waits on a lock that a long-running transaction is holding — and then blocks everything queued behind it. Always set a lock timeout.

    08 — DESIGN

    The system design round

    For a full-stack role this is usually product-shaped — design a URL shortener, a notification system, a collaborative editor — not “design Google”. They're watching your process far more than your answer.

    The five moves, in order

    1. Requirements, out loud. Who uses it, what must it do, what's explicitly out of scope. Get agreement before drawing anything. Spending five minutes here is not slow — skipping it is the most common failure in the round.
    2. Scale, in numbers. Daily active users, reads per second, writes per second, item size. Rough is fine; the point is that every later decision has a number behind it. 1M DAU with 10 actions a day is ~115 writes/sec average, call it 1,000 at peak — which is a single Postgres box, and saying so is a good answer.
    3. The API first. Three or four endpoints with their shapes. This forces the data model and keeps the discussion concrete.
    4. Data model, then storage choice. In that order — the shape of the data and its access patterns choose the store, never the reverse.
    5. One bottleneck, one fix. Pick the thing that breaks first, address it, name what the fix costs. Repeat only if there's time.
    The trap

    Reaching for Kafka, sharding, and a microservice mesh for a system with a thousand users. Proposing scale nobody asked for reads as inexperience, not ambition. “This fits on one Postgres instance with a read replica; here's the number that would change my mind” is a senior answer.

    Design a URL shortener.

    Testing The canonical warm-up. They want to see the process, and specifically that you notice it's read-heavy.

    Requirements. Create a short code for a URL; redirect on visit; optional custom alias; optional expiry; click analytics. Out of scope: editing, user accounts.

    Scale. Say 100M URLs, 10:1 read/write. That's the defining fact — it's overwhelmingly a read system, so it's a caching problem, not a write-throughput problem.

    API. POST /links {url, alias?} → 201 {code}; GET /:code → 301/302 redirect.

    Codes. Two options, and name the tradeoff: base62 of an auto-increment id is compact, collision-free, and guessable/enumerable; a random 7-character code needs a uniqueness check but is unguessable. For public links, random — enumerable short links leak everyone's URLs.

    Data. One table keyed by code, with the URL, creator, created_at, expires_at. The redirect is a single primary-key lookup, so cache it — the mapping is immutable once created, which makes it the easiest thing in the world to cache. That's the key insight: immutable data has no invalidation problem.

    Redirect status. 301 is cached by browsers forever, which kills your analytics and makes expiry impossible; 302 keeps every hit coming to you. Choose based on whether you want the traffic. Noticing this at all marks you out.

    Analytics. Don't write a row synchronously on the redirect path — the redirect must stay fast. Fire an event onto a queue and aggregate asynchronously.

    Design a notification system (email, push, in-app).

    Testing Queues, retries, idempotency, fan-out. The most common “real” full-stack design prompt.

    The shape: producers emit events → a queue → workers resolve preferences and fan out to channel adapters (email, push, in-app) → each adapter talks to a third-party provider.

    The design points that matter, all of which come from one fact — third-party providers fail and time out:

    • Never send inline with the request. A provider timeout must not fail the user's action.
    • Idempotency. Queues deliver at-least-once, so a retried message must not send twice. Deduplicate on a notification key before dispatch. This is the single most important word in this design.
    • Retries with exponential backoff and jitter, then a dead-letter queue. Jitter matters: without it, every retry after a provider outage arrives simultaneously and knocks it over again.
    • Preferences and quiet hours checked at send time, not enqueue time — the user may have unsubscribed in between.
    • Digest and rate limiting per user, so one noisy event source can't send 400 emails.
    • Templates versioned, with the rendered payload stored for support and debugging.

    If they ask about in-app real-time: WebSockets or SSE for connected clients, with a durable inbox table as the source of truth so a disconnected user isn't skipped. The socket is an optimisation; the table is the guarantee.

    Design the system you already built — a shared research cache for agents.

    Testing Nothing beats designing a system you've actually operated. If they let you choose the prompt, choose this.

    Lead with the framing that makes it interesting: it's a cache whose keys are natural-language questions, so the two hard problems are what counts as a cache hit and when does an entry go stale. Both have real answers in your build:

    • Hit criterion. Not string equality — semantic equivalence. Hybrid retrieval (vector ∪ lexical), a hard scope gate, fusion, and a conservative threshold. Tuned toward misses because a false hit serves a wrong answer with a citation attached.
    • Staleness. No fixed TTL, because different facts rot at different rates. Confidence decays exponentially from the last corroboration, with the half-life set by a volatility class — 180 days, 3 days, 6 hours. Serve only above a threshold. Corroboration moves the anchor and re-earns confidence.
    • Correction. Disagreement supersedes rather than edits — the old record is retired with a pointer to its replacement, and retired records are filtered out at the store level so a known-wrong answer can't be served again. The full chain stays for audit.
    • Trust. Per-depositor trust and independent corroboration counts, so one bad actor can't poison a topic on their own.

    Then the line that ties it to engineering rather than research: the trust and confidence pipeline is deterministic on purpose — no model judges whether a claim is still true. Matching is the one place a model is allowed to decide. That's an auditability constraint, and it's exactly the sort of self-imposed boundary that reads as senior.

    How do you cache, and how do you invalidate?

    Testing Comes up in almost every design round. You have a genuine production scar here — use it.

    Layers, outermost first: browser cache, CDN, an application cache such as Redis, the database's own buffer cache. Cache as close to the user as the data's tolerance for staleness allows.

    Strategies: cache-aside (read cache, miss → read database → populate) is the default; write-through keeps them consistent at the cost of write latency; write-behind is fast and can lose data.

    Invalidation, in preference order: (1) make the data immutable and key by content or version, so nothing ever needs invalidating — this is what your versioned blob writes do, and what bundlers do with hashed filenames; (2) explicitly evict on write; (3) TTL, which is really just choosing how wrong you're willing to be.

    Then name the failure you actually hit: a cache is only correct for data that tolerates staleness, and authentication data does not. Overwriting one blob key meant a signup could be invisible to the very next request. Also mention the stampede — when a hot key expires, every concurrent request misses at once and hammers the origin; fix with a short lock, or by refreshing slightly before expiry.

    The coding round

    Build a tree from a flat list of items with parent ids.

    Testing The single most likely practical question. Real (comment threads, nav menus, category trees) and it separates O(n) from O(n²) thinking.

    function buildTree(rows) {
  const byId = new Map();
  for (const r of rows) byId.set(r.id, { ...r, children: [] });

  const roots = [];
  for (const r of rows) {
    const node = byId.get(r.id);
    const parent = r.parentId == null ? null : byId.get(r.parentId);
    if (parent) parent.children.push(node);
    else roots.push(node);          // root, or an orphan whose parent is missing
  }
  return roots;
}

    Two passes, O(n) time and space. The first pass exists so the second never has to search for a parent — that's the whole trick, and saying it aloud is the point.

    Edges to raise yourself: a missing parent id (orphan — drop it, or promote it to a root, but ask); a cycle, which this silently tolerates but which would infinitely recurse in any renderer, so detect it if the data is untrusted; and stable ordering, which follows input order here and may need an explicit sort.

    Implement debounce. Then throttle. What's the difference?

    Testing Closures, this, and timers in one question. A front-end classic.

    function debounce(fn, wait) {
  let t;
  return function (...args) {
    clearTimeout(t);
    t = setTimeout(() => fn.apply(this, args), wait);
  };
}

function throttle(fn, interval) {
  let last = 0;
  return function (...args) {
    const now = Date.now();
    if (now - last >= interval) { last = now; fn.apply(this, args); }
  };
}

    Debounce waits for the activity to stop — one call after the last event. Use it for a search-as-you-type field, where only the final query matters. Throttle guarantees at most one call per interval regardless of how long activity continues — use it for scroll and resize handlers, where you want steady updates during the event, not one at the end.

    Details that earn credit: function rather than an arrow so this binds from the call site, and offering a cancel() method for cleanup in a React effect — a pending debounced call firing after unmount is a real bug.

    Run N async tasks with a concurrency limit of K.

    Testing Whether your promise knowledge is real. Promise.all over 10,000 URLs starts 10,000 requests at once — that's the bug being probed.

    async function pool(items, k, worker) {
  const results = new Array(items.length);
  let next = 0;

  const runner = async () => {
    while (next < items.length) {
      const i = next++;                       // claim an index, then await
      results[i] = await worker(items[i], i);
    }
  };

  await Promise.all(Array.from({ length: Math.min(k, items.length) }, runner));
  return results;
}

    K workers each pull the next index until the list is exhausted — a worker that finishes early picks up more work, so it self-balances. Incrementing next before any await is what makes the claim atomic; JS is single-threaded, so no two workers can interleave between the read and the increment.

    Follow-ups to pre-empt: results stay in input order because you write by index; a rejected task currently kills the pool, so wrap the worker if you want allSettled semantics; and this is the right place to mention retries with backoff and an AbortController deadline if the tasks are network calls.

    Here's a component with a bug. Find it.

    Testing Debugging under observation, which is closer to the actual job than any algorithm question.

    Work the list out loud in this order — it's roughly the frequency order of real React bugs:

    1. Stale closure — an effect or callback capturing an old state value because a dependency is missing from the array.
    2. Missing cleanup — a subscription, timer, or fetch that outlives the component.
    3. Mutating state — arr.push(x); setArr(arr). Same reference, so no re-render.
    4. Index keys in a reorderable list.
    5. Async setState from a stale value — setCount(count + 1) twice in a row; needs the updater form setCount(c => c + 1).
    6. Race condition in a fetch effect — the slow response overwriting the fast one.

    Say what you're checking as you check it. “Let me look at the dependency arrays first, that's where this usually lives” demonstrates a method, which is what's being scored — and it still scores if the bug turns out to be somewhere else.

    10 — DELIVERY

    Testing, CI, and shipping

    Your CI is a genuinely good answer — it gates on a quality metric, not just green unit tests. Most candidates have nothing like that to point at.

    What do you test, and what don't you?

    Testing Judgment, not doctrine. “Test everything” and “100% coverage” are both wrong answers.

    Test behaviour at the boundaries of a unit, not its internals — a test that breaks when you rename a private function is a liability, because it makes refactoring expensive and teaches people to delete tests.

    Where the value is, by tier: heavy unit testing of pure logic with real branching — your confidence decay, the agreement gate, scope conflict resolution, all pure functions with clear inputs and outputs; integration tests at the API boundary, hitting a real database rather than a mocked one, because the interesting bugs live in the SQL and the serialisation; and a small number of end-to-end tests over the two or three flows that lose you money if they break — signup, login, publish.

    What not to test: framework behaviour, getters, and anything where the test restates the implementation. On coverage: useful as a signal about which files are untouched, worthless as a target — the moment it's a goal, people write tests that execute lines without asserting anything.

    Walk me through your CI pipeline.

    Testing Whether you've thought about feedback speed and what a build is allowed to block on.

    Yours has three properties worth naming explicitly, because each is a deliberate decision:

    • Path-filtered. The workflow only runs when rrsrch/** or the workflow itself changes, so a front-end commit doesn't wait on a Python suite that can't be affected by it.
    • Hermetic and offline. CI installs a light dependency subset and runs against an in-memory store with a deterministic hash embedder. No Postgres, no Torch, no network. The heavy Postgres and MiniLM variants run on the deployment box instead. That's the fast/slow split: the fast checks gate the merge; the slow ones run where the real infrastructure is.
    • It gates on quality, not just correctness. Beyond 93 unit tests, make eval runs a matching evaluation with explicit exit criteria — paraphrase hit rate, approximately zero scope false-hits, zero intent false-hits — and exits non-zero if any regresses. So a change that keeps every test green but makes retrieval worse still fails the build.

    That last point is the one to dwell on. Framed generally: if your product's core value is a measurable metric, that metric belongs in CI as a gate. It's the same argument as a performance budget failing a build on bundle size. Very few candidates bring an example of it.

    What you'd add next: linting and type checking as required checks (you have ruff and mypy configured but not wired into the workflow), and a preview deployment per pull request.

    Production is down. Walk me through the first fifteen minutes.

    Testing Incident instinct. The order matters more than the tools.

    1. Restore service before diagnosing. If a deploy correlates with the outage, roll back first and investigate from a healthy state. Understanding the bug is not the emergency.
    2. Communicate early. A short status note with what's affected and when you'll next update. Silence is what turns an outage into a crisis.
    3. Establish blast radius — all users or some, all endpoints or one, reads or writes. This narrows the cause faster than reading logs.
    4. Check what changed. Your deploy, a dependency, a provider, a certificate, a quota. Your own blob incident is the perfect illustration: nothing in the code changed — the edge started refusing an anonymous read. Something outside your deploy pipeline changed.
    5. Mitigate, then fix. Feature-flag the broken path off if you can.
    6. Blameless write-up afterwards with a timeline, contributing causes, and one or two concrete follow-ups. Include the detection gap — how long between breaking and noticing — because that's usually the most valuable finding.

    If you get the chance, land the point from your own incident: the root cause was diagnosable only after you made two different failures distinguishable in the logs. Observability work is what makes the next incident short.

    How do you review someone else's pull request?

    Testing Whether you'd be good on a team. Often asked as the last question by a senior engineer.

    Read the description first — if you can't tell what problem it solves, that's the first comment. Then correctness at the boundaries (nulls, errors, concurrency), then whether the tests would actually catch a regression, then design, then style last — and style should be a linter's job, not a human's.

    On tone: separate blocking concerns from suggestions explicitly, ask questions rather than issue instructions when you might be missing context, and approve with minor comments rather than blocking on nits — a review round trip costs a day and nits don't justify it. Say what's good, briefly; a review that's only criticism trains people to fear review.

    Your repo shows you'd be a good reviewer already, and it's worth saying why: the comments explain why, not what. “Every failure below used to return [], which reads downstream as 'this store is empty' — indistinguishable from 'we could not read it'. Those are opposite problems.” That's the reasoning a reviewer needs, left in the code where the next person finds it.

    Tell me about a technical decision you'd make differently now.

    Testing Growth. A fake weakness (“I care too much”) fails this outright.

    Use the account store, in STAR order and tightly: Situation — needed accounts on a serverless deploy with no database provisioned. Task — ship auth without a week of infrastructure work.     Testing Whether you can disagree without it becoming personal, and whether you can lose gracefully.

    Solo project? Say so and reframe honestly — do not invent a colleague.
